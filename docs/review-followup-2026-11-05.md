# Исправления по внешнему ревью — 5 ноября 2026

Проверены и исправлены пункты 1–7 раздела «Баги» из переданного ревью. Базовая версия — `d08fcff`. Изменения рекомендаций, новые функции модерации и остальные предложения из текста не включены в этот набор исправлений.

## Воспроизводимые ошибки и результат

| Пункт | Ошибка | Поведение после исправления |
| --- | --- | --- |
| 1 | Текст сообщения бота, начинающийся с `/pause` или `/delete`, выполнялся вместо действия кнопки | Команда берётся только из входящего пользовательского `message`; callback всегда обрабатывается по собственному payload |
| 2 | Изменение анкеты, фильтров, языка или скрытие показанного человека мешало отправить жалобу | Последний серверный токен сохраняет право блокировки и жалобы; лайк и пропуск изменённой анкеты отклоняются |
| 3 | Откат системного времени блокировал действия до прежнего времени `last_request` | Кратковременный ограничитель использует `time.monotonic()` и ограниченную память процесса, без записи SQL на каждую проверку |
| 4 | Неизвестный старый интерес приводил к исключению при чтении профиля или черновика | Чтение отбрасывает неизвестные или некорректные интересы, учитывает текущий лимит и нейтрально обрабатывает старую цель знакомства; новые записи проверяются строго |
| 5 | Ошибка подтверждения callback прекращала обработку допустимого действия | Ошибка подтверждения записывается только по типу, затем действие проходит обычную проверку токена, владельца и прав |
| 6 | Следующая карточка ждала рассылки до 25 чужих уведомлений | Обработчик сначала завершает ответ пользователю, затем запускает одно объединённое фоновое задание; очередь остаётся в SQLite |
| 7 | Сохранённый username мог уже принадлежать другому человеку | Перед контактом выполняется `get_chat` по числовому ID; применяется полученный username или ссылка по ID, с повторной проверкой пары после сетевого ожидания |

Для подтверждения до исправлений запускались регрессионные проверки команд в сообщениях бота, ошибок подтверждения, устаревших контактов, изменения адресата жалобы, отката часов, старых тегов и блокирующей отправки уведомлений. Ошибки воспроизвелись. Требование сохранения неразрывного пробела в настоящем Telegram не использовалось: проверялся сам ошибочный разбор текста сообщения бота.

## Проверки

- **275 тестов пройдены**, включая 84 новые проверки относительно базовой версии.
- Ruff: анализ и форматирование пройдены; `pip check` не нашёл несовместимых зависимостей.
- Реальный Telegram SDK работает с подставным сетевым транспортом. В сквозном тесте текст всех сообщений с callback задан как `/pause`, чтобы проверить и кнопки регистрации, и реакции, и другие переходы.
- Регрессионные проверки исключают поддельные, чужие, заменённые, использованные токены и токены удалённого аккаунта после повторной регистрации. Сбой записи жалобы откатывает блокировку и сохраняет возможность повторить действие.
- Проверены изменение контакта без нового входящего сообщения, удалённый username, ошибка и неверный ID ответа `get_chat`, блокировка во время запроса, `RetryAfter` и отсутствие раскрытия контакта при одностороннем лайке.
- Настоящий `Application` и `JobQueue` с подставным Telegram проверяют объединение 200 запросов фоновой отправки, восстановление после ошибки и ожидание работающего отправителя при остановке.

Симуляция 1000 временных пользователей проверяет 3000 запросов ленты, 250 пар и 500 взаимных уведомлений, независимый эталон фильтров, восстановление после перезапуска и целостность SQLite. Отдельно проверен поиск на 10 000 анкетах: по 30 последовательных измеряемых запросов в широком пуле, с историей лайков и со строгими фильтрами. Эти проверки используют временные базы и подставной Telegram; это не 10 000 одновременных реальных подключений.

Команды воспроизведения:

```sh

python -m ruff format --check .

python scripts/simulate.py --users 1000 --requests 3000 --matches 250 --report data/review-simulation.json
```

## Совместимость и ограничения

Схема остаётся версии 3; новая миграция не нужна. Сохранённые профили, пары, очереди и черновики продолжают использоваться. Мягкое чтение не переписывает исходные интересы в базе; актуальные значения сохраняются при следующем редактировании владельцем.

Право пожаловаться остаётся у последней открытой карточки и не разрешает выбрать произвольный Telegram ID. Снимка прежнего текста и фотографии в жалобе пока нет. Переход в меню, получение новой карточки или начало другого сценария может отозвать предыдущий токен.

Непринятый Telegram ответ на callback не доказывает недопустимость самого действия, но серверный токен всё равно проверяется и расходуется один раз. Повторное нажатие не создаёт второй лайк или вторую пару.

Фоновое задание не гарантирует мгновенной отправки при очереди, сетевых ошибках или лимитах Telegram. При остановке ещё не запущенное одноразовое задание может не выполниться; сохранённую очередь подхватит периодическая отправка после следующего старта. Доставка остаётся «как минимум один раз» при аварии между принятием сообщения Telegram и записью результата.

Запрос актуального username уменьшает риск устаревшей ссылки, но уже отправленная ссылка не обновляется при будущих изменениях Telegram. При ошибке используется ссылка по ID, доступность которой зависит от настроек Telegram. Реальная доставка и открытие контактов требуют отдельной проверки с токеном и двумя аккаунтами.

Основание для использования `get_chat`: [Telegram Bot API — getChat](https://core.telegram.org/bots/api#getchat). Фоновый запуск использует [JobQueue установленной версии PTB 22.8](https://docs.python-telegram-bot.org/en/v22.8/telegram.ext.jobqueue.html).
